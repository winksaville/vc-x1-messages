# m-15-0 a clone per member, the remote as the mutex

Wink's idea, 2026-11-17, discussed in a zc-ring-x1 session and sent here because the work is
vc-x1's: the messages repo is a data base, not a dual repo, so the protocol change and the tool
that runs it belong in vc-x1. These are findings, not a decision, and Wink moves the discussion
to vc-x1.

## The idea

Each member clones the messages repo into its own workspace at `.family-messages`, instead of
every member sharing one clone at `../vc-x1-messages`.

- No ownership: no `owner` file, no take and release, and no human clearing a take left by a
  session that died.
- The same path for every member, so `[family] messages` reads alike everywhere.
- Other machines can take part, which the README's "No second machine" rules out today.
- A workspace no longer depends on a sibling directory existing.

## The finding

A clone per member removes the local mutex but not its job, the allocation of ids. Two clones
can both read `threads` as 14 and open thread 15, or both append line 3 to one thread. The
remote can take the job, and the thread files stay exactly as they are: one file per thread,
numeric ids, and the `threads` counter. Only the write procedure changes:

1. Fetch and move to the remote's `main`.
2. Read messages, so the write answers the traffic as it stands.
3. Append the line, or open the thread and bump `threads`, commit, and push.
4. A rejected push: drop the commit, return to step 1, and write again.

The remote accepts one push on top of a given commit, so two members never both land the same
id. A line is a pure append and its number is its position, so a retry is a rewrite and never a
merge, and nothing conflicts. The README's "an id is final only once pushed" becomes the whole
allocation rule.

## What it costs

- Every write is a commit and a push. A line is not written until it is pushed, so "an
  uncommitted line is as visible and as final as a pushed one" goes, and each member's
  `custom.md` needs a standing permission for these pushes, as for the fetch.
- No offline writes. A line can be drafted without the remote, not numbered.
- A retry may be a rethink. A line that arrived in the same thread is read before the write is
  made again, which is what step 2 is for.
- A body file is renamed on a retry, its name carrying the line's number. Mechanical, and a
  `vc-x1` subcommand could run the whole loop.
- The nested repo: `.family-messages/` goes into each work-repo's `.gitignore`, an agent-repo
  inside the workspace must not pick it up either, and `rg` from the workspace root skips a
  dot-directory without `--hidden`.

## What gets easier

The version commit. With nothing unpushed counting as written, it is one more push like any
other, and "every member's last push already in `main@origin`" holds by construction.

## Alternatives looked at and passed over

- One file per line, with member-scoped ids, `open/m-12/zc-ring-x1-1.md`: conflict-free with no
  retry, but the numbers no longer order a thread and a conversation is no longer one file. Wink
  was not taken with it.
- Member-scoped ids in the one file, merged by git's union merge: loses "line `<num>` is file
  line `<num>` plus two", and jj does not honour git merge attributes.
- One file per member per thread: reading a conversation means interleaving files.

Each buys concurrent offline writes, which we think the family's traffic does not need.

## Open

- Whether the clone is plain git or jj-colocated.
- It is a protocol version bump, and the cutover retires `owner` and the shared clone.
